# План фикса: воспроизведение обрывается на ~60 с из-за срыва разбора аттестации

Составлен 2026-10-01. Симптом: видео играет примерно минуту и замирает, дальше не идёт.

## 1. Что НЕ является причиной

| Версия | Почему отпадает |
|---|---|
| Полоса просмотра (правка `6b6f477`/`c69fb28`) | Первое `page context unavailable` в `cache/play.log` — **12:50:07**, а новая сборка плеера установлена в 13:51 и приложение перезапущено в 13:54. Срыв разбора начался на час раньше. Плюс `status:3` приходит из `sabr_bridge.mjs`, которого правка не касалась вообще |
| `YOUHUB_NO_PAGE_CTX=1` в окружении | Не задана ни в `YouHub.sh`, ни в `~/.zshrc`/`~/.bashrc`/`~/.profile`, ни в окружении живого процесса |
| Лимит по IP / «стена» | Механика ниже объясняет всё, включая перемежаемость; отдельной стены не требуется |

## 2. Причина (доказана измерениями)

`_fetchPageContext()` (`po_token.mjs:86`) достаёт челлендж BotGuard из главной страницы, вырезая
**фиксированное окно** `html.slice(at - 4000, at + 40000)` вокруг слова `bgChallenge` (`:96`) и
разбирая поля регуляркой `"name":"([^"]+)"`.

Значение `program` — это байткод BotGuard, и он **почти упирается в это окно**:

| Замер (8 запросов главной) | Значение |
|---|---|
| Длина `program`, обычные ответы | 38 695 … 39 111 символов |
| Начало `program` относительно `bgChallenge` | +226 |
| Конец `program` | +38 921 … +39 237 |
| Конец окна | +40 000 |
| **Запас** | **≈ 900 символов (2%)** |
| `globalName` | сразу за `program`, на +38 934 … +39 250 |

Когда YouTube отдаёт программу на 5–10% длиннее, окно режет её **в середине значения**:

| Замер на сбойных ответах | Значение |
|---|---|
| `program` | 40 371 и 42 899 символов |
| Конец `program` | +40 597 и +43 125 (за окном) |
| `globalName` | +40 610 и +43 138 — **в окно не попадает вовсе** |

Регулярка требует закрывающую кавычку, а окно обрывает строку раньше → `program = null`;
`globalName` стоит следом и не попадает в окно целиком → `globalName = null`. `interpreterUrl`
(≈ +80) и `eventId` (ищется по всему HTML, `:93`) при этом находятся — **это ровно сигнатура из
лога**:

```
[po_token] page context unavailable (homepage context incomplete
  (eventId=true program=false globalName=false interpreterUrl=true))
  — falling back to the InnerTube challenge
```

**Частота: 1 срыв на 8 запросов** (первый прогон), поэтому баг перемежающийся и выглядел как
«иногда работает».

### Что происходит дальше

Разбор сорвался → код молча уходит на InnerTube-челлендж (`:154`) → PO-токен **без контекста
страницы** → SABR даёт холодный допуск на 1–2 МБ → `stream protection status:2 → 3` → поток
умирает примерно на 53–60 с. Это тот самый механизм, который в `899d30c` починили для
InnerTube-пути, — но починка опирается на разбор главной, а он теперь срывается.

Видно в логе за 13:56–13:59 (ролик `nH1UBXOWQHQ`, 300 с):

| Сессия | Что получено | Итог |
|---|---|---|
| #1 | 788 КБ видео / 1,0 МБ аудио, буфер до 53,3 с | `File ended prematurely`, watchdog переоткрыл на 53,3 с |
| #2 | 191 КБ / 180 КБ | `not enough bytes from new session (25.1s) — giving up` |
| #3 | — | `status:3` с первых секунд |

Watchdog и перезапуск **работают штатно** — отказ приходит снаружи, и каждый новый сеанс
повторяет ту же ошибку, потому что перечеканка токена идёт тем же сломанным путём.

## 3. Фикс проверен на живом сбойном образце

Поймал ответ с `program` = 40 371 (окно его режет) и прогнал оба способа разбора:

| Способ | `program` | `globalName` | `interpreterUrl` |
|---|---|---|---|
| Текущий (фиксированное окно) | **null** | **null** | ok |
| Предлагаемый (разбор по скобкам) | ok, 40 371 символов | ok, `trayride` | ok |

То есть правка лечит именно сбойный случай, а не «должна помочь по идее».

## 4. Правка

### 4.1 `po_token.mjs` — `_fetchPageContext()`: убрать зависимость от размера окна

Вместо `slice()` с магическим числом — взять объект `bgChallenge` целиком по балансу скобок:

1. декодировать **весь** HTML (`_decodeEscapes` по ~900 КБ — миллисекунды);
2. найти `"bgChallenge":`, от следующей `{` пройти вперёд с балансом скобок, учитывая строки и
   экранирование, до парной `}` — это и есть текст объекта;
3. поля (`program`, `globalName`, `...TrustedResourceUrlWrappedValue`) читать тем же `_field` уже
   из этого текста.

Размер объекта перестаёт что-либо значить: 40 КБ, 400 КБ — разбирается одинаково.

**Поле `challenge` вернуть не получится, и это не потеря:** оно лежит не внутри `bgChallenge`, а
рядом с ним (`{"challenge":"a=6\&…","bgChallenge":{…}}`), и **нигде не используется** — вызывающий
код (`:145`) берёт только `program`, `globalName`, `interpreterUrl` (проверено). Либо убрать его из
возвращаемого объекта, либо искать отдельно; тащить в разбор не нужно.

### 4.2 `po_token.mjs` — ретрай перед фолбэком

Срывы **случайны на запрос** (1 из 8), поэтому 2–3 попытки главной дают ~99% успеха даже без
правки парсера. Фолбэк на InnerTube оставить последним средством, а не первым.

### 4.3 `po_token.mjs` — сделать срыв заметным

Сейчас `page context unavailable` — одна строка среди сотен `stream protection`, и заметить её
можно только целенаправленным `grep`. Добавить однозначный маркер (например
`[po_token] FALLBACK: …`), чтобы будущая диагностика начиналась с одного `grep`.

### 4.4 Что НЕ трогать

`ffplay-yt/ffplay.c`, `bridge_player.py`, `sabr_bridge.mjs`, `auth_cookies.py` — к причине
отношения не имеют. Соблазн «поправить заодно» здесь только добавляет риск.

### 4.5 Отдельная задача (не в этом фиксе)

После `giving up` плеер просто замирает на последнем кадре — пользователь не понимает, что поток
прерван и ролик надо перезапустить. Показ сообщения в плеере — самостоятельная правка; с
исправленной аттестацией она перестаёт быть срочной.

## 5. Как проверять

1. **Детерминированно, без сети:** тест на разбор — синтетический HTML с объектом, где `program`
   длиннее любого прежнего окна (и с `\x22`-экранированием, как на живой странице). На текущем
   коде такой тест обязан падать, на исправленном — проходить. Это единственная проверка, которая
   не зависит от того, какой ответ отдаст YouTube в момент прогона.
2. **A/B по потоку, без окна плеера:** `scripts/hs_probe.py <vid> 90` — с фиксом ожидается
   `status:1` и весь ролик; `YOUHUB_NO_PAGE_CTX=1 … hs_probe.py <vid> 90` как контроль — обрыв
   около 64 с.
3. **Живая приёмка:** в `cache/play.log` есть `page context ok` и нет `FALLBACK`; объём медиа
   растёт до конца ролика. Критерий — `stream protection status` и объём полученного медиа, а
   **не** размер токена: по прежнему замеру размер не является признаком валидности.
4. Прогнать `test_seek.py` и `test_watchdog.py` — правка их не касается, но пусть подтвердят, что
   ничего не задето.

## 6. Риски и обязательные мелочи

- **Один запрос — один коммит:** сам фикс разбора, ретрай и логирование разбирать по отдельным
  коммитам, иначе нельзя откатить по одному.
- **`NOTICE`** дополнить: `po_token.mjs` в списке изменённых уже есть, но описание правки
  изменится (GPLv3 §5a требует заметного уведомления с датой).
- **`LICENSE` не трогать**, `cache/` не коммитить.
- После правки — **перезапустить приложение**: запущенный процесс держит старый `po_token.mjs`
  в памяти моста.
- Если после фикса срывы останутся, смотреть `_fetchPageContext` дальше: следующая по вероятности
  причина — отсутствие `bgChallenge` на странице целиком (согласие/урезанная разметка), и тогда
  ретрай из 4.2 станет основным лечением, а парсер — вторичным.

## 7. Порядок работ

1. Тест на разбор (падающий на текущем коде) — зафиксировать причину в коде, а не только в тексте.
2. Правка разбора по скобкам → тест зелёный.
3. Ретрай + маркер `FALLBACK` в логе.
4. `hs_probe.py` A/B, затем живая приёмка.
5. `NOTICE`, `История_диалогов.md`, коммиты, публикация — по обычному порядку.
