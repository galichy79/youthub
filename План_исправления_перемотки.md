# План: починка перемотки вперёд (youthub)

Составлен 2026-10-01 по живому логу `cache/play.log` (запуск 12:50–12:55, видео `i6uDq1VaF44`).
Задача для ИИ-исполнителя: устранить баг «стрелка вперёд показывает оверлей, но видео не перематывается».

---

## 1. Симптом (подтверждён пользователем)

| Направление | Что видит пользователь |
|---|---|
| `→` (+10 с) | Оверлей перемотки появляется, видео **не двигается**. Через 6–11 с сессия SABR перезапускается, все нажатия за это время молча выброшены |
| `←` (−10 с) | Оверлей появляется, **перемотка работает** |

Ключ: сообщение на экране — не признак успеха. Оверлей рисуется локально в `ffplay-yt` **до** отправки запроса контроллеру и показывается, даже если контроллер откажет (это осознанное решение, см. `ffplay-yt/ffplay.c:1499-1507` и `:132-136`).

---

## 2. Корневая причина (доказана, не гипотеза)

`bridge_player.py:785` `_handle_seek_req()` решает, можно ли перемотать внутри уже скачанного файла:

```python
played_in_file = max(self._last_pos_sec - self._file_start_sec, 1.0)   # :804
bytes_per_sec  = (size / played_in_file) if size > 0 else 0            # :805
target_bytes   = target_offset_sec * bytes_per_sec                     # :807
in_range = (target >= self._file_start_sec
            and target_bytes > 0
            and target_bytes < size - SEEK_SAFETY_BYTES)               # :808-812
```

Обозначим: `S` — размер файла, `F` — `_file_start_sec`, `P` — плейхед, `T` — цель.
Подставим `bytes_per_sec = S / (P − F)`:

```
target_bytes = (T − F) · S / (P − F)
in_range  ⟺  (T − F) · S / (P − F)  <  S − 2 МБ
          ⟺  (T − F) / (P − F)       <  1 − 2 МБ/S
          ⟺  T ≲ P
```

**Условие `in_range` структурно неспособно пропустить перемотку вперёд.** Знаменателем взято время, которое пользователь *уже проиграл* (`played_in_file`), а не длительность медиа, которое *уже лежит на диске*. Сессия SABR отдаёт весь бёрст сразу на скорости сети (в логе: 249 МБ за ~107 с при длительности видео 1591 с — вчетверо быстрее реального времени), поэтому `P − F` в разы меньше реально скачанной длительности, `bytes_per_sec` завышен, `target_bytes` вылетает за размер файла — всегда.

Следствие: каждое нажатие `→` уходит в `_restart_at()` (`:818-822`) — полный перезапуск сессии SABR (убить сессию, вычеканить PO Token, поднять новую, ждать 4 МБ прайминга, `OPEN`). В логе это 6.1 с и 10.8 с. Пока идёт перезапуск, `_handle_seek_req` выбрасывает все нажатия (`:789-792`).

| `play.log:6490-6496` | шесть `SEEK_REQ_REL -10.0 … in_range=True` | **Назад проходит** — ровно как предсказывает неравенство `T < P` |
| `play.log` | `in_range=False` — 33 шт., `IGNORED (restart in progress)` — 130 шт. | Масштаб: почти все нажатия либо перезапускают сессию, либо выбрасываются |

### Сплошной подсчёт по всему логу (проверка 2026-10-01, сессия ещё шла)

| Направление | Решений | `in_range=True` | `in_range=False` |
|---|---|---|---|
| `→` вперёд | 26 | **0** | 26 |
| `←` назад | 23 | 14 | 9 |

**Вперёд не прошло ни разу — 0 из 26, при любом размере файла** (от 6.5 МБ до 249 МБ), то есть в том
числе когда на диске лежало всё видео целиком. Назад проходит ровно тогда, когда `pos > fileStart`.

Отдельно видны 9 провалов на `←` — это дефект №2 в чистом виде: сразу после перезапуска
`play.log:6527` даёт `pos=124.1 fileStart=128.4` — мост стартовал с кейфрейма раньше запрошенной
точки, `pos − fileStart < 0`, и проверка ломается даже для перемотки назад.

## 3. Сопутствующие дефекты (в том же узле, чинить вместе)

| # | Дефект | Где | Почему важно |
|---|---|---|---|
| 2 | `_file_start_sec` = **запрошенная** позиция (`start_at`), а не фактическое начало медиа | `:884-888` | В логе `fileStart=14.8`, а POS приходит `10.1`: мост стартует с кейфрейма **до** запрошенной точки. Из-за этого `pos − fileStart < 0`, обрезается до `1.0` — метрика врёт ещё сильнее. Смещение надо брать из файла (`pts[0]`), а не из запроса |
| 3 | Нажатия во время перезапуска исчезают | `:789-792` | Пользователь нажимает 40 раз → 130 строк `IGNORED` → видео оказывается не там, куда он целился. Нужно запомнить **последнее** намерение и применить его после перезапуска |
| 4 | Кулдаун 0.5 с не сбрасывается после перезапуска | `:795-798`, `SEEK_COOLDOWN_SEC` | Первое осмысленное нажатие после долгого перезапуска может быть отброшено |
| 5 | `_media_end_sec()` дорогой и меряется редко | `:590-621` | Полный `ffprobe` по всем пакетам; вызывается только вотчдогом после 12 с тишины. В горячий путь его звать нельзя — нужен кэш |

Важно: **вотчдог уже знает правильную формулу** — его комментарий на `:532-543` прямо описывает, что при бёрсте плейхед стоит в начале, а файл уже докачан до конца, и поэтому судить надо по файлу, а не по плейхеду. Правку вотчдога (коммит `cfe0514`) в путь перемотки не перенесли. Это и есть баг.

## 4. План правок

### Шаг 1. Единая метрика «докуда скачано» (`bridge_player.py`)

1. Добавить в `LivePlayer` кэш: `_media_span: Optional[tuple[float, float, float]]` — `(first_pts_abs, last_pts_abs, measured_at_monotonic)`.
2. Выделить из `_media_end_sec()` (`:590-621`) дешёвый измеритель `_measure_media_span() -> Optional[tuple[float,float]]`, возвращающий **абсолютные** `pts[0]` и `pts[-1]` (сейчас функция возвращает `_file_start_sec + (pts[-1] − pts[0])` — подмешивает доверенное значение к измеренному, от этого и берётся дефект №2).
3. Обновлять кэш:
   * в фоновом потоке вотчдога (он и так тикает каждые 2 с) — когда размер файла изменился или прошло > 2 с; **и**
   * лениво в `_handle_seek_req`, если кэш пуст или старше TTL (1.0 с).
   Для больших файлов ограничить `ffprobe` хвостом (`-read_intervals`), чтобы не сканировать 250 МБ на каждое нажатие. Замер: 16 МБ / 3390 пакетов — 0.135 с; кэш с TTL убирает стоимость из горячего пути.

### Шаг 2. Починить решение о перемотке (`_handle_seek_req`, `:785-822`)

```python
span = self._media_span_abs()          # кэш; None → фолбэк на текущее поведение
if span is None:
    ...                                # прежняя арифметика, чтобы не сломать деградацию
else:
    first_abs, last_abs = span
    downloaded = max(last_abs - first_abs, 1.0)          # длительность медиа на диске
    bytes_per_sec = size / downloaded
    played_rel = self._last_pos_sec - first_abs          # играем ОТ ФАКТИЧЕСКОГО начала
    target_rel = target - first_abs
    target_bytes = target_rel * bytes_per_sec
    in_range = (target_rel > 0
                and target_bytes > 0
                and target_bytes < size - SEEK_SAFETY_BYTES)
```

Плюс: явно писать в лог `downloaded=…s last=…s` — тогда следующий разбор не потребует догадок.

Ожидаемый эффект: цель внутри скачанного → `SEEK_REL` (< 100 мс, мгновенно); за краем скачанного → честный перезапуск. Перезапуск остаётся, но становится редким исключением, а не нормой.

### Шаг 3. Не терять нажатия (дефект №3, №4)

* Заменить ранний `return` при `_restart_lock.locked()` (`:789-792`) на накопление: `self._pending_delta = delta_sec` (перезапись — нужно только последнее намерение).
* В конце `_restart_at()` (`:895-897`, после успешного `OPEN`) применить накопленное: `if self._pending_delta: delta, self._pending_delta = self._pending_delta, None; self._handle_seek_req(delta, cprint)`.
* Сбрасывать `self._last_seek_at = 0.0` после завершения перезапуска, чтобы кулдаун не съел первое нажатие.
* Диагностику `IGNORED` оставить, но добавить в неё `pending=…`, чтобы потеря не была бесшумной.

### Шаг 4. Проверить сторону ffplay (без пересборки, если не понадобится)

`SEEK_REL` (`ffplay-yt/ffplay.c:2490-2497`) вызывает `stream_seek(is, target, inc_us, 0)` — абсолютная перемотка по времени, механика верная, и в логе она уже работала для `←`. Правок в C **не требуется**, пока шаги 1–3 дают `SEEK_REL` для вперёд. Пересобирать бинарь только если после правки `→` начнёт уходить в `SEEK_REL`, но видео всё равно не двинется (тогда смотреть `stream_seek` и переполнение `target`).

## 6. Что НЕ делать

| Антипаттерн | Почему |
|---|---|
| Увеличивать `SEEK_SAFETY_BYTES` / крутить порог | Неравенство `T ≲ P` от порога не зависит — вперёд не заработает никогда |
| Вешать `SEEK_REL` без проверки, «пусть ffplay сам разберётся» | На недокачанном файле ffplay упрётся в конец и встанет на паузу (`File ended prematurely`) |
| Гнать полный `ffprobe` на каждое нажатие | 250 МБ файл — сотни мс в горячем пути; нужен кэш |
| Пересобирать `ffplay-yt` «на всякий случай» | C-сторона уже проверена логом: `SEEK_REL` для `←` работает |
| Затирать `cache/play.log` при отладке | Это единственный источник правды по этому багу; копировать, а не перезаписывать |
