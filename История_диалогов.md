# История диалогов — YouHub

**YouHub** — консольный YouTube-клиент: TUI-сетка превью (kitty graphics protocol), воспроизведение до 1080p60 через реверс-инженерный протокол SABR, кастомный плеер `ffplay-yt` (форк FFplay 4.3.9 с IPC), рекомендации, поиск, SponsorBlock, watchstats. Без браузера и без yt-dlp в пути воспроизведения.

- Точка входа: `grid_demo.py`
- Окружение: Python 3.11 (`.venv`), Node.js ≥ 18, системный FFmpeg, kitty, X11
- Репозиторий: https://github.com/HelpFreedom/youthub.git

### 2026-09-30 — Диагностика обрыва воспроизведения

**Запрос:** воспроизведение останавливается, выяснить причину.

**Симптом:** видео играет ~72 с, затем намертво замирает на последнем кадре. На экране никакого сообщения. `cache/play.log` перестаёт расти, `/tmp/ytlive_<id>_s0_*.mkv` замирает на ~20 МБ.

**Причина — эскалация защиты YouTube на SABR-потоке («attestation required»):**

```
[bridge] session #1 stream protection {"status":2,...}   ← аттестация в процессе
[bridge] session #1 stream protection {"status":3,...}   ← аттестация ТРЕБУЕТСЯ
[ERROR] [SabrStream] Maximum retries (10) exceeded ...: attestation required
[bridge] session #1 video pump error: ... attestation required
[matroska,webm] File ended prematurely
```

**Механика:** PO Token передаётся в `SabrStream` (`sabr_bridge.mjs:502`); YouTube шлёт `STREAM_PROTECTION_STATUS` (2 = pending, 3 = required); `SabrStream.js:790` на статусе 3 **бросает исключение**; оно всплывает в pump-цикле (`:533`), насосы встают, ffmpeg закрывает входы, `.mkv` финализируется досрочно, ffplay получает `File ended prematurely` и застывает.

**Почему нет самовосстановления:**
1. PO Token чеканится один раз на контекст (`:341-370`) и переиспользуется всеми сессиями, включая post-seek.
2. У `SabrStream` есть `setPoToken()` (`SabrStream.d.ts:112`) — ровно для этого случая, но мост его не вызывает (на `streamProtectionStatusUpdate` только пишет лог, `:507`).
3. Мост не сообщает оркестратору о смерти сессии: IPC знает только `START_SESSION`/`STOP_SESSION` (`:567-579`), `bridge_player.py` слушает лишь `POS`, `SEEK_REQ_REL`, `PLAY_VIDEO`, `CONTINUATION`.
4. Нет watchdog'а на рост файла; `_restart_at()` (`bridge_player.py:556`) вызывается только из обработчика перемотки.
5. Не обрабатывается `reloadPlayerResponse` («текущая сессия недействительна») — тоже завершает поток исключением.

**Подтверждение диагноза:** перезапуск клиента лечит — при старте чеканится свежий PO Token. Значит дело в устаревшем токене, а не в сети или плеере.

**Предложенные варианты починки (решение пользователя ожидается):** A — watchdog на стагнацию `.mkv` в оркестраторе; B — перечеканка PO Token + `sabr.setPoToken()` в мосту (корневая причина); C — обработка `reloadPlayerResponse`; D — куки через `extract_cookies.py` (сейчас `[watchstats] no cookies`, запросы анонимные). Рекомендация: B + A, дополнительно C.

**Версии зависимостей:** `googlevideo` 4.0.4, `youtubei.js` 17.0.1.

**Немедленный обход:** `q` → перезапуск (свежий токен); либо перемотка, которая поднимает новую сессию, но со старым токеном.

### 2026-09-30 — Обрыв воспроизведения: починка (варианты A + B)

**Запрос:** реализовать варианты B (перечеканка PO Token в мосту) и A (watchdog в оркестраторе).

#### Что сделано

**B — `sabr_bridge.mjs`**
- `ctx.visitorData` / `ctx.poTokenStale` — состояние токена.
- `refreshPoToken(reason)` — перечеканка с дедупликацией одновременных вызовов; свежий токен отдаётся живому потоку через `SabrStream.setPoToken()` и следующей сессии.
- `maybeRefreshPoToken(reason)` — то же, но с кулдауном 90 с (статус 2 приходит и в норме, сразу после старта).
- Подписка на `streamProtectionStatusUpdate`: статус 2 → профилактическая перечеканка; статус 3 → `poTokenStale = true` + перечеканка под кулдауном.
- `startSession()`: если токен помечен устаревшим — чеканить новый **до** открытия `SabrStream`.
- Ответ `START_SESSION` дополнен `duration_ms=` — чтобы оркестратор отличал «поток умер» от «видео докачано».

**A — `bridge_player.py`**
- Константы `STALL_TIMEOUT_SEC=12`, `STALL_POLL_SEC=2`, `STALL_END_MARGIN_SEC=5`, `STALL_MAX_FAILURES=4`.
- Поля `_duration_sec`, `_stall_failures`; `_parse_session_reply()` для разбора ответа моста.
- Поток `_watchdog_loop`: следит за ростом tmpfile; при замерзании вызывает существующий `_restart_at()`; при отказе моста — экспоненциальный backoff до 120 с; после 4 неудач останавливается с понятным сообщением.

#### Найденный и исправленный баг в `po_token.mjs`

Повторная чеканка давала **растущий** токен: 124 → 216 → 304 байта (+~88 за вызов). Причина — minter (`webPoSignalOutput[0](itBytes)`) создавался заново на каждую чеканку, а замыкание snapshot накапливает состояние. Minter кэшируется; проверено — три чеканки подряд дают по 124 байта. Без этой правки починка B была бы бесполезной.

#### Исправление логики watchdog'а по ходу

Первая версия требовала остановки **и** файла, **и** плейхеда. Не срабатывала: после обрыва ffplay продолжает гнать мастер-часы, POS растёт, хотя картинка замерла — таймер сбрасывался бесконечно (подтверждено: файл замер в 01:46:05, поток жив, срабатывания нет и через 35 с). Переделано: признак — только замерзание файла, а точка возобновления — позиция плейхеда **в момент последнего прихода данных** (не текущая). Побочно это дало надёжный различитель: «видео докачано целиком» останавливается у самого конца (и отсекается защитой по `duration_ms`), «поток умер» — задолго до конца.

#### Результат проверки

Механика работает — подтверждено логом:

```
[watchdog] no new data for 12s (last data at 3.6s of 1878.0s, clock now 15.6s) — reopening session
[restart] BEGIN -> 3.6s
[bridge] PO Token refresh (stale token before new session) bound to videoId=nnIQPt-3T5c
[bridge] PO Token refreshed: 124B in 2ms
[bridge] session #2 → /tmp/…_s1_cn74rea9.mkv  start_at=3556ms
[restart] DONE OPEN … (5.8s)
```

Watchdog замечает обрыв, перечеканка даёт корректный токен (124 Б), сессия поднимается за 5.8 с, возобновление — с 3.6 с (буферизованный хвост переигрывается, а не пропускается: часы уже ушли на 15.6 с).

#### Но воспроизведение всё равно не восстанавливается

Каждая новая сессия гибнет на `attestation required` за считанные секунды. Решающий факт: **сессия #1, чей токен чеканился полным свежим BotGuard-челленджем при старте процесса, отвергнута так же.** Значит нынешний отказ не связан с устареванием токена — отвергается и «эталонный» стартовый токен.

Наиболее вероятно: IP/visitor жёстко челленджится после часа повторных автоматических прогонов. Собственное сообщение кода на этот случай: «Likely your IP is temporarily rate-limited; wait 15-60 min or change the proxy». Следующий рычаг — куки (вариант D, `extract_cookies.py`), которые дают аутентифицированную сессию и снижают bot-скоринг.

Вывод: A и B реализованы и работают — они лечат именно тот сценарий, ради которого делались (молчаливый обрыв + протухший токен). Текущий блокер — на стороне YouTube.

### 2026-09-30 — Петля на первых секундах: watchdog возвращал назад

**Запрос:** после слияния видео воспроизводится, но зацикливается на первых минутах.

**Симптом в логе** (`cache/play.log`, запуск с рабочего стола — фикс Node работает, `node: …/v22.23.2/bin/node (v22.23.2)`):

```
[restart] BEGIN -> 3.5s          → session #2 start_at=3522ms
[watchdog] no new data for 12s (last data at 3.6s of 2990.0s, clock now 15.6s) — reopening session
[restart] BEGIN -> 3.6s          → session #3 start_at=3554ms
```
Точка возобновления не растёт (3.5 → 3.6 с) — плеер по кругу играет первые ~15 с.

**Причина.** Сессия отдаёт весь свой «залп» сразу, а потом умирает. Поэтому «позиция плейхеда в момент последнего прихода данных» — это всегда секунда-две **после точки возобновления предыдущего перезапуска**. Каждый рестарт попадал в ту же секунду. Прежнее правило («возобновляться там, где плейхед был при последних байтах, чтобы переиграть буфер, а не пропустить») в этом режиме превращается в вечный цикл.

**Измерено (не оценено):**
- одна сессия = **17.30 МБ = 61.3 с медиа** (финализированный файл, `format=duration`);
- при 17.30 МБ в момент решения watchdog'а (`ffmpeg` ещё жив) `format=duration` = **N/A**, но последний PTS **читается**: видео 55.956 с, аудио 55.914 с. То есть истинный конец медиа известен и на живом файле;
- перезапуск случался на ~15-й секунде при 61 с медиа на диске — выбрасывалось ~45 с недосмотренного буфера.

**Сделано (`bridge_player.py`, коммит `7b32b90`):**
- новый метод `_media_end_sec()` — последний PTS пакета через ffprobe (видео, при неудаче аудио), span + `_file_start_sec`; корректно и при абсолютных, и при нормализованных таймстемпах. Не удалось прочитать → `None`, откат на плейхед;
- watchdog: (1) пока `POS < media_end - STALL_BUFFER_MARGIN_SEC` — **не перезапускать**, дать буферу проиграться (стена часто сама отпускает), с потолком `STALL_WAIT_MAX_SEC` на случай паузы; (2) перезапуск — ровно в `media_end`. Кэш `media_end` сбрасывается при приходе новых байт;
- обновлена докстрока функции: старое правило описано как ошибочное.

**Проверено:** `_media_end_sec()` на реальном файле → 61.26 с (start_at=0) и 661.26 с (start_at=600, сдвиг учитывается), отсутствующий файл → `None`. Настоящий `_watchdog_loop` прогнан на заглушке плеера: при плейхеде 15 с и медиа до 61 с — перезапуска нет, в логе «letting the buffer play out»; при плейхеде 67 с — перезапуск на 61.26 с.

**Чего ожидать:** видео идёт кусками по ~60 с с коротким провалом на стыке (стена на стороне YouTube рубит загрузчик), но **вперёд**, без петли. Если загрузчик оживает сам — перезапуска не будет вовсе.

### 2026-10-01 11:30–11:45 — Найдена и устранена настоящая причина обрыва: аттестация BotGuard

**Запрос:** «Проект youthub продолжай».

**Отправная точка.** Запуск в 11:30:54 (ролик `q13s8aq__RI`, 717 с) после **11,5 часов покоя** — и стена сразу: сессия #1 отдала 4,3 МБ, `status:2` → `status:3` через **1 секунду** после старта, буфер доигран до 55,2 с, рестарт дал 844 КБ и сдался. Это опровергало модель «накопительный лимит, восстанавливается покоем»: покой был максимальный, а отказ пришёл мгновенно.

**Что перепроверили и отбросили:**
- `googlevideo` 4.0.4 → 4.1.1 — в `handleStreamProtectionStatus` тот же `throw` на `status === 3`, изменений по аттестации нет;
- `youtubei.js` 17.0.1 → 18.1.0 — то же;
- привязка PO-токена (videoId vs visitorData) — не она;
- гипотеза «лимит по `visitorData`» из плана — **не подтвердилась**, см. ниже.

**Корень найден.** Reverse-engineering-цепочка вывела на PR InfinityLoop1308/PipePipeClient #86 «use the page-native BotGuard attestation context». Симптом в описании совпал буквально: *«without EVENT_ID, status 2 around 60 seconds»*. Причина:

| Слой | Что было | Что нужно |
|---|---|---|
| Источник челленджа | InnerTube `/att/get` (`Innertube.getAttestationChallenge`) | главная страница `youtube.com` |
| Контекст страницы | снимок в jsdom-окне **без** `window.yt.config_.EVENT_ID` | `EVENT_ID` той же страницы, выставленный **до** снимка |

BotGuard аттестовал страницу, которой не было: токен имел правильную форму, но не проходил проверку SABR. Отсюда и «свежий полный челлендж не помогает» — дело было не в свежести, а в контексте.

**Фикс (коммит `899d30c`, `po_token.mjs`):** `_fetchPageContext()` тянет главную страницу тем же UA, что и jsdom, декодирует `\xNN`-экранирование вокруг `bgChallenge` и достаёт оттуда `program`, `globalName`, `interpreterUrl` и `EVENT_ID`; `EVENT_ID` выставляется в `window.yt.config_` до `snapshot()`. Путь через InnerTube сохранён как fallback; `YOUHUB_NO_PAGE_CTX=1` принудительно включает его — им и сделан контрольный прогон.

**A/B — один ролик, один IP, три минуты разницы (headless-проба, коммит `f412e6f`):**

| Путь | Защита | `attestation required` | Байт | Медиа | Итог |
|---|---|---|---|---|---|
| InnerTube (`YOUHUB_NO_PAGE_CTX=1`) | `status:2` → `status:3` | 4 | 5,2 МБ | **64,0 с** | обрыв на той самой ~минуте |
| page-native + `EVENT_ID` | **`status:1`** всё время | **0** | 65,6 МБ | **716,5 с** | отдан весь ролик |

**Вывод:** «накопитивного лимита по IP/visitor» не существовало. Все прошлые наблюдения (обрыв на ~60 с, «перемежающаяся стена», «через 40 минут покоя заработало») объясняются одним: невалидный контекст аттестации, который сервер иногда прощал. Лечение — не пауза и не смена IP, а правильный снимок BotGuard.

**Инструмент:** пробу перенесли из `/tmp` в `scripts/hs_probe.py` (план это и предусматривал) — поднимает мост без плеера, шлёт `START_SESSION`, меряет рост файла и последний видео-PTS, считает события защиты.

**Изменённые/созданные файлы:**
- `po_token.mjs` — page-native челлендж + `EVENT_ID`, fallback на InnerTube (коммит `899d30c`)
- `scripts/hs_probe.py` — новый headless-пробник (коммит `f412e6f`)
- `История_диалогов.md`, `План_решения_стены.md` — эта запись и отметка о решении

**Что осталось:** живая приёмка — запустить сетку из kitty и убедиться, что ролик играется целиком (headless-проба показала, что поток отдаёт весь файл, но ffplay и watchdog в связке проверялись в последний раз до фикса).
