# План поэтапного решения проблемы с блокировкой потока

**Для кого этот документ:** для ИИ-ассистента, который продолжит работу над `/home/u/youthub`.
Читать целиком перед началом. Все факты ниже проверены на этой машине — не переоткрывать их заново.

**Проблема:** воспроизведение обрывается. Поток `googlevideo` отвечает `stream protection {"status":3}` / `attestation required`, новые сессии получают 0–2 МБ и умирают. Клиент при этом работает корректно (watchdog и возобновление по концу медиа проверены).

**Цель плана:** выяснить, к чему именно привязан лимит YouTube, и выбрать обход по факту, а не по догадке.

**Критерий успеха:** ролик играется от начала до конца без обрыва **и** известно, какой параметр (visitor / IP / аккаунт) расходует лимит.

---

## 1. Что уже известно (не перепроверять)

| Факт | Как установлено |
|---|---|
| Лимит **накопительный** по числу сессий | 2026-09-30: после 40 мин покоя тот же ролик отдал 84 МБ целиком, до этого — `403` |
| Bearer (OAuth) на стену **не влияет** | Парный тест: с Bearer 84.3 МБ и без Bearer 84.3 МБ |
| Протухание PO Token **не причина** | 2026-10-01 00:00: `status:3` прилетел на сессии со свежим полным BotGuard-челленджем, отчеканенным при старте |
| Смена IP **не помогла** | Тест через точку доступа телефона — тот же отказ |
| Куки влияют только на `watchstats` | В пути воспроизведения уже Bearer; куки на челлендж не влияют |
| `playerResponse` получается стабильно | Слой `/watch` работает: ротация 24 TLS-стратегий справляется |
| Отказывает **слой потока**, не слой входа | README upstream описывает обход для `/watch`; для потока там ничего не обещано |
| Логика клиента исправна | `7b32b90` (возобновление по концу медиа), `59924a6` (backoff 60/120/240 + `STOP_SESSION`) — подтверждены вживую |

**Открытая гипотеза, которую и проверяет этот план:** лимит считается по `visitorData` / зрительскому профилю, а не по IP и не по аккаунту.

## 2. Антипаттерны — чего НЕ делать

| Не делать | Почему |
|---|---|
| Гонять тесты подряд | Каждая сессия продлевает лимит. За вечер 2026-09-30 их набралось 87 |
| Считать короткий headless-тест (4–17 с) доказательством | Защита не успевает сработать — из-за этого был сделан **ошибочный** вывод «виноват конкретный ролик» |
| Тестировать в живом окне, когда хватает headless | Занимает экран и добавляет сессии (запуск = 2 сессии: первая + авто-повтор) |
| Убивать окно через `pkill -f` | Остаётся осиротевший `sabr_bridge.mjs` (проверено: висел 44 мин с `PPID=1`) и `pkill -f` убивает собственную оболочку. Выход — клавиша `q` или `kill <PID>` |
| Коммитить пачку правок одним коммитом | Правило пользователя: одна просьба — один коммит |
| Пушить в `origin` и ставить теги | Чужой upstream (`HelpFreedom/youthub`); пуш только по явной просьбе |
| Затирать старые логи и заметки | Правило пользователя: прежние версии сохранять |

**Проверенный приём для измерений:** у незафинализированного `.mkv` `format=duration` = `N/A`, но последний PTS читается:
```bash
ffprobe -select_streams v:0 -show_entries packet=pts_time -of csv=p=0 <файл> | tail -1
```
Ориентир: **17.3 МБ ≈ 61 с медиа**.

## 4. Этапы

### Этап 0. Гигиена и покой (ожидание 40–60 мин)

1. Убедиться, что нет процессов и мусора:
   ```bash
   pgrep -af 'sabr_bridge|grid_demo'; ls -la /tmp/ytlive_* 2>/dev/null
   ```
   Найдены сироты — `kill <PID>` (не `pkill -f`), мусорные сокеты и `.mkv` — `rm -f` по явным путям.
2. Сохранить срез лога, **не перезаписывая**:
   ```bash
   cp cache/play.log cache/play.log.$(date +%F_%H%M).snapshot
   ```
3. Ничего не запускать 40–60 минут.

**Переход к этапу 1:** прошло ≥ 40 мин покоя, процессов нет.

---

### Этап 1. Измерение порога сессий

**Вопрос:** сколько сессий подряд отдаёт YouTube после полного покоя?

1. Перенести пробу в репозиторий (чтобы не потерялась):
   ```bash
   cp /tmp/hs_long.py scripts/hs_probe.py
   ```
2. Протокол: после покоя запускать **по одной** сессии с паузой 60 с между ними, каждую — минимум 75 с (короче нельзя, см. антипаттерны). После каждого прогона фиксировать в таблицу:

| # сессии | Время | Байт получено | Медиа, с | Статусы в логе | Итог |
|---|---|---|---|---|---|
| 1 | | | | | |
| 2 | | | | | |

3. Остановиться на **первом отказе** (0–2 МБ, `status:3`) + одна контрольная проверка.

**Критерий:** получено число `N` — «бюджет сессий на цикл покоя».

**Стоп-условие:** как только пошёл отказ — прекратить, не добивать.

---

### Этап 2. Локализация лимита (по одному тесту за цикл покоя)

Каждый тест — **после паузы 40–60 мин**, ровно одна сессия. Между тестами ничего не запускать.

| Тест | Что делаем | Что означает результат |
|---|---|---|
| **2.1 Свежий visitor** | Отложить `cache/oauth.json` и `cache/innertube_*.json` в сторону (не удалять), запустить одну сессию | Пошло → лимит привязан к `visitorData` / зрительскому профилю |
| **2.2 Анонимный поток** | Вернуть временную диагностическую переменную `YOUHUB_NO_BEARER` (отдельной веткой, не в `main`), прогнать | Пошло → лимит на аккаунте. Не пошло → дело не в аккаунте |
| **2.3 Внешний IP** | Прокси SOCKS5/HTTP через переменные окружения. **В системе прокси нет — сначала спросить пользователя** | Пошло → лимит по IP, нужен пул |
| **2.4 Контроль** | Ничего не менять, после той же паузы | База для сравнения: сколько отдаёт «как есть» |

**Важно:** тест 2.2 требует временной правки в `sabr_bridge.mjs`. Делать её в отдельной ветке, в `main` не тащить, после теста откатить (это уже делалось 2026-09-30).

**Итог этапа:** таблица «параметр → помог/не помог», из неё выбирается ветвь этапа 3.

---

### Этап 3. Выбор решения по результату

| Что показали тесты | Решение |
|---|---|
| Помог свежий visitor | Ротация зрительского профиля перед каждой N-й сессией (см. 4.4) |
| Помог только прокси | Пул прокси + ротация; в проекте уже есть поддержка `HTTPS_PROXY` |
| Помог только анонимный режим | Анонимный режим по умолчанию для потока + `yt-dlp` как fallback |
| Не помогло ничего | Режим «экономного просмотра» (см. 4.1, 4.2) + обязательный `yt-dlp` fallback (4.3) |

---

### Этап 4. Правки в коде

**Правило:** каждая правка — отдельный коммит, отдельная проверка. Порядок: правка → `py_compile` → тест на заглушке (без окна и без YouTube) → живой прогон → коммит.

| Правка | Файл | Суть | Статус |
|---|---|---|---|
| **4.1 Экономия сессий** | `bridge_player.py` | Отложить авто-повтор `first session empty`, сделать задержку настраиваемой. **По умолчанию — как сейчас** (повтор иногда спасает) | Не сделано |
| **4.2 Кулдаун при `status:3`** | `bridge_player.py` | Пока идёт `status:3`, не перезапускать каждые 60/120/240 с, а ждать N минут | Не сделано |
| **4.3 Fallback на `yt-dlp`** | `bridge_player.py` | SABR отказал → скачать ролик `yt-dlp` и отдать в `ffplay-yt` | Не сделано |
| **4.4 Ротация visitor / прокси** | `sabr_bridge.mjs`, `pr_fetch.py` | По результату этапа 3 | Не сделано |

**Как проверять логику watchdog без ожидания YouTube:** взять настоящий `bp.LivePlayer._watchdog_loop`, вызвать на заглушке с полями `log_path / tmpfile / _shutdown / _restart_lock / _last_pos_sec / _duration_sec / _file_start_sec / _stall_failures / _restart_at`, подменив `STALL_TIMEOUT_SEC` и `STALL_POLL_SEC` на малые. Своих полей заглушке не добавлять.

---

### Этап 5. Приёмка и фиксация

1. Один живой прогон: ролик играется без обрыва (или ≥ 10 мин без обрыва).
2. Замерить: сколько сессий потрачено, рост буфера, был ли `status:3`.
3. Дописать в `История_диалогов.md`: что делали, какие ветви проверены, что вышло.
4. Обновить память проекта (`memory/youthub.md`) — состояние на дату.
5. Если выбрана ветвь с ограничениями (например, «не больше N сессий в час») — вынести это в README проекта отдельным разделом.

## 6. Правила ведения работ (напоминание)

- Одна просьба — один коммит.
- Теги не ставить (чужой проект). Пуш — только по явной просьбе.
- Прежние версии файлов и логов не затирать.
- Перед слиянием с upstream — страховочная ветка; сверять upstream до работы над багом.
- После правок кода приложение **перезапускать**: запущенный процесс держит старый `bridge_player` в памяти.
- Выходить из плеера клавишей `q`.
